## Overview

`Volatility` is an open-source memory analysis framework, implemented in
Python, composed of numerous plugins.

[`Volatility 3`](https://github.com/volatilityfoundation/volatility3) is a
complete rewrite of `Volatility 2`, with notable changes such as the
replacement of the `Volatility 2` profiles by symbol tables (automatically
downloaded / generated for Windows memory images), and the automatic
identification of the memory image format. `Volatility 2` is archived and no
longer supported, and the `Volatility 3` 2.26.0 release (May 2025) aimed at
functional parity with `Volatility 2`. `Volatility 3` should thus be used,
`Volatility 2` being documented below for older memory images and plugins that
have not been ported.

The frequent release of new Windows versions makes the support of the latest
versions a challenge for memory analysis tools, as the kernel structures
definitions and symbols must be kept up to date. This is partially why the
`Rekall` memory analysis tool (based on a fork of `Volatility`) was
discontinued. `Volatility 3` addresses this challenge by automatically
downloading the symbols of the analyzed Windows kernel from the Microsoft
symbol server (with the correct `PDB` determined directly from the memory
image) and generating the corresponding symbol tables.

`Volatility 3` supports the following memory image formats:

  - Raw / padded memory images.
  - `LiME` and compressed `AVML` memory images.
  - Windows crash dumps (full and bitmap dumps, but not kernel or small
    dumps).
  - `VMware` memory files (`vmem`, with the associated `vmss` / `vmsn` file,
    refer to the
    [virtual machines memory acquisition note](./acquisition_virtualmachines.md#vmware-memory-and-state-files)).
  - `ELF` core dumps (such as `VirtualBox` or `QEMU` core dumps), `QEMU`
    suspend files, and `Xen` core dumps.

## Basic usage

`Volatility` works using plugins, executed individually.

*Volatility 3*

The metadata determined for a memory image (such as the kernel offset) can be
saved, and reused to speed up subsequent executions, using respectively the
`--save-config <CONFIG_FILE>` and `-c <CONFIG_FILE>` options.

```bash
# Installs Volatility 3 (the "full" extra installs the optional dependencies, such as yara-python).
pip install "volatility3[full]"

# vol is the entry point installed with pip ("python3 vol.py" from a clone of the repository).
# -r <quick | pretty | csv | json | jsonl>: output format ("quick" by default, "pretty" improving the formatting).
# -o <OUTPUT_DIR>: output directory of the files generated by the plugins (such as dumped processes or files).
vol [-r pretty] [-o <OUTPUT_DIR>] [--save-config <CONFIG_FILE> | -c <CONFIG_FILE>] -f <MEMORY_DUMP_FILE> <PLUGIN> [<PLUGIN_OPTIONS>]

# Complements the analysis of a Windows memory image with the page file (pagefile.sys), acquired at the same time as the memory image.
vol --single-swap-locations <PAGEFILE_SYS> -f <MEMORY_DUMP_FILE> <PLUGIN>

# Lists the plugins, and the options of a given plugin.
vol -h
vol <PLUGIN> -h

# Creates a timeline from the time-related information of the plugins (processes creation and exit, network connections, registry keys LastWriteTime, etc.), optionally as a body file.
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> timeliner.Timeliner [--create-bodyfile]
```

*Volatility 2*

```bash
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> <PLUGIN>

# If a custom profile is needed, for example for Linux memory image analysis (profile as a ZIP file).
volatility --plugins=<FOLDER_WITH_PROFILE_ZIP> -f <MEMORY_DUMP_FILE> --profile=<PROFILE> <PLUGIN>

# The VOLATILITY_LOCATION and VOLATILITY_PROFILE environment variables can be used in place of the command line options to specify the memory dump file and the profile.
export VOLATILITY_LOCATION=file://<MEMORY_DUMP_FILE_PATH>
export VOLATILITY_PROFILE=<PROFILE>
volatility <PLUGIN>
```

## Windows memory analysis

### Windows plugins overview

`Volatility` implements two main types of plugins, each using a distinct
approach:

  - The "list" plugins, which navigate through kernel data structures to
    extract information from memory. Plugins implementing this approach work
    similarly to the native operating system `APIs` (and are thus vulnerable to
    the same anti-forensics techniques).

  - The "scan" plugins, which carve the memory for known data structures, such
    as `EPROCESS` objects. While slower and more prone to false positives, this
    approach can retrieve information on objects no longer referenced by the
    operating system (such as processes that have exited) or hidden using
    anti-forensics techniques.

The following `Volatility 2` plugins (either included in the base code or
from the community) can be useful for memory analysis, a number of them being
ported, under a different naming nomenclature, to `Volatility 3`. Since
`Volatility 3` 2.26, a number of plugins were moved to the `windows.malware`
and `windows.registry` namespaces (for instance, `windows.malfind.Malfind`
became `windows.malware.malfind.Malfind`), the previous names being
deprecated.

Not all the plugins below are compatible with every operating system version.

### Image identification

`Volatility 3` does not rely on profiles, and the `windows.info.Info` plugin
can be used to retrieve information on the memory image (operating system
version, kernel base address, etc.).

For `Volatility 2`, the `imageinfo` and `kdbgscan` plugins can be used to
retrieve the profile of the image, needed for further analysis. `imageinfo`
provides basic information on the image, such as the operating system,
service pack, and hardware architecture of the original system, as well as
the time the sample was collected and suggested `Volatility` profiles.
Contrary to `imageinfo`, `kdbgscan` is designed to positively identify the
correct profile, by scanning for `KDBGHeader` signatures linked to `Volatility`
profiles. **It is thus recommended to retrieve the `Volatility 2` profile of
the image using the `kdbgscan` plugin.**

```bash
# Volatility 3.
vol -f <MEMORY_DUMP_FILE> windows.info.Info

# Volatility 2.
volatility -f <MEMORY_DUMP_FILE> imageinfo
# Recommended for the profile identification.
volatility -f <MEMORY_DUMP_FILE> kdbgscan
```

### Processes listing

The `pslist`, `pstree`, `psscan`, and `psxview` plugins can be used to list
the processes in the memory of the system. **It is recommended to start the
processes analysis using the `psxview` plugin, as it integrates multiple
techniques for `rootkit` detection.**

The `Volatility 2` `psxview` plugin combines multiple sources to list both
linked and unlinked / hidden processes, and shows which technique(s) detected
each process:

  - The `pslist` and `psscan` plugins, both of which are detailed below.

  - The `thrdscan` plugin, which scans the memory for `executive thread
    (ETHREAD)` objects (used by the system scheduler), and uses the `EPROCESS`
    block of the data structure to identify the process the thread belongs
    to.

  - The `PspCidTable` data structure, which keeps track of all the processes
    and threads.

  - The handle table of the `Windows subsystem process (csrss.exe)` and its
    internal independent structures.

  - The `sessions` plugin, which analyzes the unique `_MM_SESSION_SPACE`
    objects and, among other features, displays the details related to the
    processes running in each logon session.

  - The `deskscan` plugin, which enumerates desktops, desktop heap
    allocations, and associated threads.

The `Volatility 3` `windows.malware.psxview.PsXView` plugin relies on four of
these methods (`pslist`, `psscan`, `thrdscan`, and the `csrss.exe` handles).

The `pslist` plugin prints the processes in the list pointed to by
`PsActiveProcessHead`, and the `pstree` plugin orders the results of the
`pslist` plugin in a hierarchical tree form, from parent to child
process(es). Both plugins retrieve the process name, `process ID (PID)`,
`parent process ID (PPID)`, number of threads, number of handles, and the
dates of creation and exit of the processes, but cannot detect rogue unlinked
processes.

The `psscan` plugin lists the processes by scanning the entire memory image
for `_POOL_HEADER` structures, and automatically performs sanity checks to
reduce false positives. The `_POOL_HEADER` structure is prepended to each
memory allocation made by the kernel whenever an object (process, file, etc.)
is created in memory, and identifies the subsequent object type in its
`PoolTag` field. The `Proc` tag is used to identify processes, and parsing the
memory for `_POOL_HEADER` structures with the `PoolTag` field set to `Proc` can
thus be used to identify processes, including unlinked ones.

```bash
# Volatility 3.
vol -f <MEMORY_DUMP_FILE> windows.malware.psxview.PsXView
vol -f <MEMORY_DUMP_FILE> windows.pslist.PsList [--pid <PID>]
vol -f <MEMORY_DUMP_FILE> windows.pstree.PsTree [--pid <PID>]
vol -f <MEMORY_DUMP_FILE> windows.psscan.PsScan

# Volatility 2.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> psxview
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> pslist
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> pstree
# Graph output format, that can be opened using xdot.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> pstree --output=dot --output-file=<OUTPUT_DOT_FILE>
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> psscan
```

### DLLs listing

The `dlllist` and `ldrmodules` plugins can be used to list the `DLLs` loaded
in the memory of the system. **It is recommended to start the analysis of the
loaded `DLLs` using the `ldrmodules` plugin, as it integrates multiple
techniques for `rootkit` detection.**

The `dlllist` plugin lists the loaded `DLLs`, of all processes or of the
specified process, by walking the list of `_LDR_DATA_TABLE_ENTRY` structures
pointed to by the `InLoadOrderModuleList` of the `Process Environment Block
(PEB)` of each process. `DLLs` are automatically added to this list when a
process calls the `LoadLibrary` function (or its derivatives), and are not
removed until the `FreeLibrary` function is called and the reference count of
the `DLL` reaches zero. However, `rootkits` may hide `DLLs` by unlinking them
from one or all of the linked lists of a process's `PEB`
(`InLoadOrderModuleList`, `InMemoryOrderModuleList`, and
`InInitializationOrderModuleList`), in which case the `dlllist` plugin will
not be able to identify the hidden `DLL(s)`.

The `ldrmodules` plugin parses the `Virtual Address Descriptor (VAD)` tree
(referenced in the `VadRoot` attribute of the process's `_EPROCESS` object) of
each, or of the specified, process to find `_FILE_OBJECT` structures. The base
address and the full path on disk of the memory-mapped files can be
cross-referenced with the `DLL` lists of the process's `PEB` to find rogue
unlinked `DLL(s)`.

```bash
# Volatility 3.
vol -f <MEMORY_DUMP_FILE> windows.dlllist.DllList [--pid <PID>]
# The physical offset of the EPROCESS object of an unlinked process can be retrieved using the windows.malware.psxview.PsXView (with --physical-offsets) or windows.psscan.PsScan (with --physical) plugins.
vol -f <MEMORY_DUMP_FILE> windows.dlllist.DllList --offset <EPROCESS_PHYSICAL_OFFSET>
vol -f <MEMORY_DUMP_FILE> windows.malware.ldrmodules.LdrModules [--pid <PID>]

# Volatility 2.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> dlllist [-p <PID>]
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> dlllist --offset=<EPROCESS_PHYSICAL_OFFSET>
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> ldrmodules -v [-p <PID>]
```

The `Volatility 2` `impscan` plugin can be used to scan for calls to imported
functions by a process or in a specified memory range. Scanning for calls in a
memory range can for instance be used to determine the functions called by a
malware living only in memory.

```bash
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> impscan -p <PID>

# If malfind detects a PAGE_EXECUTE_READWRITE memory page for example:
#   Process: IEXPLORE.EXE Pid: 2044 Address: 0x7ff80000
#   Vad Tag: VadS Protection: PAGE_EXECUTE_READWRITE
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> impscan -p <PID> -b <ADDRESS>
```

### Handles

The `handles` plugin displays the open handles of all processes or of the
specified process, by walking the `HandleTableList` linked list of the
`ObjectTable` (`_HANDLE_TABLE` structure) of each process's `_EPROCESS`.

The handles can be of the following types: `File`, `Directory`, `Process`,
`Thread`, `Key`, `Token`, `Mutant`, `Event`, `Port`,
`FilterCommunicationPort`, `DebugObject`, `WmiGuid`, `Controller`, `Profile`,
`Type`, `Section`, `SymbolicLink`, `EventPair`, `Desktop`, `Timer`,
`WindowStation`, `Driver`, `KeyedEvent`, `Device`, `IoCompletion`, `Adapter`,
`Job`, `WaitablePort`, `FilterConnectionPort`, `Semaphore`, and `Callback`.

```bash
# Volatility 3.
vol -f <MEMORY_DUMP_FILE> windows.handles.Handles [--pid <PID>]

# Volatility 2.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> handles [-p <PID>]
# Displays the open handles of the specified type(s).
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> handles -t <HANDLE_TYPE | COMMA_SEPARATED_HANDLE_TYPE_LIST>
```

### Processes and DLLs dump

A process's executable can be reconstructed from memory, as close as possible
to the original file, using the `procdump` / `windows.pslist.PsList --dump`
plugins, for static or dynamic reverse engineering. The full addressable
memory of a process can be dumped using the `memdump` /
`windows.memmap.Memmap --dump` plugins, to analyze the behavior of the process
on the system (runtime variables, opened files, etc.).

The `procdump` plugin uses the `ImageBaseAddress` of the process's `PEB` to
retrieve the `Portable Executable (PE)` file loaded in memory, automatically
realigns the memory sections (`.text`, `.data`, `.bss`, etc.), and performs
sanity checks on the `PE` header. Overly simplistically put, the `memdump`
plugin dumps all the memory pages of the process from its page table,
retrieved from the `DirectoryTableBase` of the `Process control block (Pcb)`
(`_KPROCESS` structure) of the process's `_EPROCESS` object.

The `dlldump` / `windows.dlllist.DllList --dump` plugins reconstruct the
`DLL(s)` from memory, for all processes or the specified process(es),
optionally filtered by `DLL` name (regex) or base address. The `DLLs` are
listed as for the `dlllist` plugin, and dumped using the `DllBase` of each
`_LDR_DATA_TABLE_ENTRY` structure.

```bash
# Volatility 3.
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> windows.pslist.PsList --dump [--pid <PID>]
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> windows.psscan.PsScan --dump [--pid <PID>]
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> windows.memmap.Memmap --dump --pid <PID>

vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> windows.dlllist.DllList --dump [--pid <PID>] [--name <REGEX> [--ignore-case]] [--base <DLL_BASE_ADDRESS>]
# Reconstructs a PE file from the specified base address in the process's memory (such as an unlinked DLL identified with windows.malware.ldrmodules.LdrModules).
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> windows.pedump.PEDump --pid <PID> --base <BASE_ADDRESS>

# Volatility 2.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> procdump -D <OUTPUT_DIR> -p <PID>
# Disables the sanity checks on the PE header, which may be exploited by malware to prevent the dumping.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> procdump --unsafe -D <OUTPUT_DIR> -p <PID>
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> memdump -D <OUTPUT_DIR> -p <PID>

volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> dlldump -D <OUTPUT_DIR> [-p <PID>]
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> dlldump -D <OUTPUT_DIR> --ignore-case --regex=<REGEX>
# Dumps the DLLs of an unlinked process, using the physical offset of its EPROCESS object (retrieved with the psxview plugin).
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> dlldump -D <OUTPUT_DIR> --offset=<EPROCESS_PHYSICAL_OFFSET>
# Dumps an unlinked DLL, using its base address (retrieved with the ldrmodules plugin).
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> dlldump -D <OUTPUT_DIR> -p <PID> --base=<DLL_BASE_ADDRESS>
```

### Processes security context and privileges

The `getsids` and `privs` plugins retrieve the `Security Identifiers (SID)`
and the privileges associated with all or the specified process(es). Both
plugins parse the `Token` attribute (`EX_FAST_REF` structure referencing a
`_TOKEN` object) of the process's `_EPROCESS` object, to retrieve,
respectively, the `SIDs` in the `UserAndGroups` attribute and the privileges
in the `Privileges` attribute.

The `UserAndGroups` attribute is an array of `_SID_AND_ATTRIBUTES` objects, of
size `UserAndGroupCount`, containing a `SID` value (`_SID` structure) and the
`SID` state in the `Attributes` flag.

The `Privileges` attribute is an array of `_LUID_AND_ATTRIBUTES` objects, of
size `PrivilegeCount`, containing a `LUID` value, representing a privilege,
and the privilege state in the `Attributes` flag (combination of the
`SE_PRIVILEGE_ENABLED`, `SE_PRIVILEGE_ENABLED_BY_DEFAULT`,
`SE_PRIVILEGE_USED_FOR_ACCESS`, and `SE_PRIVILEGE_REMOVED` values).

```bash
# Volatility 3.
vol -f <MEMORY_DUMP_FILE> windows.getsids.GetSIDs [--pid <PID>]
vol -f <MEMORY_DUMP_FILE> windows.privileges.Privs [--pid <PID>]

# Volatility 2.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> getsids [-p <PID>]
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> privs [-p <PID>]
# Displays the processes having the privilege(s) matching the regular expression.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> privs --regex="<REGEX>"
# Displays the privileges that processes explicitly enabled (i.e., that were not enabled by default but are currently enabled).
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> privs --silent
```

### Processes command line and environment variables

The `cmdline` plugin retrieves the command line arguments of all or the
specified process(es), which are stored in the `CommandLine` attribute of the
`ProcessParameters` (`_RTL_USER_PROCESS_PARAMETERS` structure) of the
process's `PEB`. The command line is specified as an argument of the
`CreateProcess` function.

Note that the command line arguments stored in the memory of a process's
`PEB` may be maliciously altered.

```bash
# Volatility 3.
vol -f <MEMORY_DUMP_FILE> windows.cmdline.CmdLine [--pid <PID>]
# --silent: suppresses the common and non-persistent variables.
vol -f <MEMORY_DUMP_FILE> windows.envars.Envars [--pid <PID>] [--silent]

# Volatility 2.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> cmdline [-p <PID>]
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> envars [-p <PID>]
```

### Network activity

Different plugins can be used to enumerate the active network connections of
the system at the time the memory image was taken. The plugins that rely on
scanning the memory for known structures may additionally retrieve
information about ended connections, as the related memory structures may
persist in memory after a connection is terminated.

```bash
# --- Windows Vista / Windows Server 2008 and later

# Scans the memory for network objects structures (TCP endpoints _TCP_ENDPOINT, TCP listeners _TCP_LISTENER, and UDP endpoints _UDP_ENDPOINT).
# Equivalent of connscan + sockscan for Windows XP and Windows Server 2003.
# --include-corrupt (Volatility 3): also displays partially overwritten (and likely corrupted) entries.
vol -f <MEMORY_DUMP_FILE> windows.netscan.NetScan [--include-corrupt]
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> netscan

# Lists the UDP endpoints (in UdpPortPool or UdpCompartmentSet), TCP listeners (in TcpPortPool or TcpCompartmentSet), and TCP endpoints (in the TCP endpoint partition table) residing in the memory space of the tcpip.sys driver.
# Starting from Windows 10 1809 (build 17763), the UdpPortPool and TcpPortPool structures were replaced by the UdpCompartmentSet and TcpCompartmentSet structures.
vol -f <MEMORY_DUMP_FILE> windows.netstat.NetStat

# --- Windows XP and Windows Server 2003 (x86 or x64) only

# Enumerates the active connections by following the TCBTable table in the memory space of the tcpip.sys driver.
# Memory images of hibernated systems may not show any connection, as Windows closes the connections before hibernating.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> connections

# Scans the memory for _TCPT_OBJECT structures.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> connscan

# Enumerates the listening sockets by following a non-exported structure in the memory space of the tcpip.sys driver.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> sockets

# Scans the memory for _ADDRESS_OBJECT sockets structures.
# May retrieve information about terminated sockets, similarly to connscan.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> sockscan
```

The `yarascan` / `windows.vadyarascan.VadYaraScan` plugins can also be used to
scan the memory image for URLs:

```bash
vol -f <MEMORY_DUMP_FILE> windows.vadyarascan.VadYaraScan --yara-string "http://"
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> yarascan -Y "http://"
```

### Files in memory

The files present in memory, i.e., the files currently loaded by processes,
can be listed and extracted using, respectively, the `filescan` /
`windows.filescan.FileScan` and `dumpfiles` / `windows.dumpfiles.DumpFiles`
plugins. The plugins scan the memory image for `_FILE_OBJECT` structures, and
thus present the advantage of being able to locate / dump files possibly
hidden by malware (as opposed to walking structures such as
`_LDR_DATA_TABLE_ENTRY`).

```bash
# Scans the memory image for FILE_OBJECT structures.
vol -f <MEMORY_DUMP_FILE> windows.filescan.FileScan
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> filescan

# Extracts all the files (_FILE_OBJECT structures) present in the memory image.
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> windows.dumpfiles.DumpFiles
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> dumpfiles -n --dump-dir=<OUTPUT_DIR> -S <OUTPUT_SUMMARY_FILE>

# Extracts the files whose names match the specified regex.
# Regex examples: ".*\.docx?$" | "\.[op]st$"
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> windows.dumpfiles.DumpFiles --filter "<REGEX>" [--ignore-case]
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> dumpfiles -n --dump-dir=<OUTPUT_DIR> -r "<REGEX>" [-i]

# Extracts the files present in the memory space of the specified process(es).
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> windows.dumpfiles.DumpFiles --pid <PID>
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> dumpfiles -n --dump-dir=<OUTPUT_DIR> -S <OUTPUT_SUMMARY_FILE> --pid=<PID | PID_COMMA_LIST>

# Extracts the file(s) (_FILE_OBJECT structure) at the given virtual / physical offset(s).
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> windows.dumpfiles.DumpFiles [--virtaddr <VIRTUAL_ADDRESS> | --physaddr <PHYSICAL_ADDRESS>]
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> dumpfiles -n --dump-dir=<OUTPUT_DIR> -Q <PHYSICAL_ADDRESS>
```

### Registry hives

The `hivelist` / `windows.registry.hivelist.HiveList` plugins can be used to
list the registry hives present in a memory image. The plugins internally rely
on the `hivescan` / `windows.registry.hivescan.HiveScan` plugins to scan the
memory for registry hives: the `_CMHIVE` data structures, used to represent
hives in kernel memory, being allocated in paged pools with the `CM10` pool
tag, the scan plugins identify paged pools with this tag. The `hivelist` /
`windows.registry.hivelist.HiveList` plugins then validate that the offsets
found by the scanner do match registry hives, by checking that the
`Signature` attribute (at offset `0x0`) of the `_CMHIVE` -> `_HHIVE` structure
is `0xbee0bee0`.

The `printkey` / `windows.registry.printkey.PrintKey` plugins can be used to
print either all or the specified registry key (and whether the key is
volatile or stable). If a registry hive is not specified (through its virtual
memory address), the plugins first enumerate the registry hives using the
`hivelist` / `windows.registry.hivelist.HiveList` plugins.

```bash
# --- Volatility 3

# Lists the registry hives, optionally filtered on the hive name, and dumps them to file (--dump).
vol -f <MEMORY_DUMP_FILE> windows.registry.hivelist.HiveList [--filter <HIVE_NAME_STRING>] [--dump]

# Prints the specified key's subkey(s) and value(s), in all or the specified registry hive(s).
# Key example: "ControlSet001\Services".
# --recurse: recursively lists the subkeys (equivalent of the Volatility 2 hivedump plugin, for the entire hive if no key is specified).
vol -f <MEMORY_DUMP_FILE> windows.registry.printkey.PrintKey [--offset <HIVE_VIRTUAL_OFFSET>] [--key "<KEY>"] [--recurse]

# --- Volatility 2

volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> hivelist

# Recursively lists the keys and subkeys (with their last written timestamp) of the specified hive.
# Virtual offset example: 0xffff860c0e681000.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> hivedump --hive-offset <HIVE_VIRTUAL_OFFSET>

# Prints the subkeys and values of all the keys.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> printkey

# Prints the specified key's subkey(s) and value(s), in all or the specified registry hive(s).
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> printkey [--hive-offset <HIVE_VIRTUAL_OFFSET>] -K "<KEY>"
```

### Strings identification

The `strings` / `windows.strings.Strings` plugins can be used to determine to
which process(es) the given strings belong. The plugins take as input a file
of strings prefixed by their (decimal) offset in the memory image, as produced
by the `strings` utility with the `-t d` option.

```bash
# Extracts the ASCII and UTF-16LE strings, with their decimal offset.
strings -a -t d <MEMORY_DUMP_FILE> > <STRINGS_FILE>
strings -a -t d -e l <MEMORY_DUMP_FILE> >> <STRINGS_FILE>

vol -f <MEMORY_DUMP_FILE> windows.strings.Strings --strings-file <STRINGS_FILE> [--pid <PID>]
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> strings -s <STRINGS_FILE>
```

### Malware detection

The `malfind` / `windows.malware.malfind.Malfind` plugins detect suspicious
memory pages that may be the result of code injection (shellcode or `DLL`
injection). The `malfind` plugins use a number of criteria, in combination,
to identify code injection:

  - Private memory region (i.e., memory without an associated mapped file).

  - Executable memory region (such as `PAGE_EXECUTE_READWRITE`).

  - Memory with a `PE` header (`MZ` magic number) with no associated entry in
    the module list of the process's `PEB`.

  - Etc.

`Volatility 3` implements additional detection plugins in the
`windows.malware` namespace, for instance to detect process hollowing,
process ghosting, process name spoofing, suspicious threads, hidden services
or drivers, or the use of direct system calls.

```bash
# Volatility 3.
# --dump: extracts the injected VADs.
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> windows.malware.malfind.Malfind [--pid <PID>] [--dump]
vol -f <MEMORY_DUMP_FILE> windows.malware.hollowprocesses.HollowProcesses
vol -f <MEMORY_DUMP_FILE> windows.malware.processghosting.ProcessGhosting
vol -f <MEMORY_DUMP_FILE> windows.malware.pebmasquerade.PebMasquerade
vol -f <MEMORY_DUMP_FILE> windows.malware.suspicious_threads.SuspiciousThreads
vol -f <MEMORY_DUMP_FILE> windows.malware.svcdiff.SvcDiff

# Volatility 2.
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> malfind
```

The `yarascan` / `yarascan.YaraScan` (kernel memory) and
`windows.vadyarascan.VadYaraScan` (processes memory) plugins can be used to
scan the memory image for `YARA` rules, or for a single string, hex string
(`{ ... }`), or regex (`/.../`). The `regexscan.RegExScan` (kernel memory) and
`windows.vadregexscan.VadRegExScan` (processes memory) `Volatility 3` plugins
can similarly be used to scan the memory image for a regex.

```bash
# --- Volatility 3
# --insensitive / --wide: case insensitive search / search for wide (UTF-16) strings (for --yara-string).
vol -f <MEMORY_DUMP_FILE> yarascan.YaraScan [--yara-file <YARA_RULES_FILE> | --yara-string "<STRING | {HEX_STRING} | /REGEX/>"] [--insensitive] [--wide]
vol -f <MEMORY_DUMP_FILE> windows.vadyarascan.VadYaraScan [--pid <PID>] [--yara-file <YARA_RULES_FILE> | --yara-string "<STRING | {HEX_STRING} | /REGEX/>"]
vol -f <MEMORY_DUMP_FILE> windows.vadregexscan.VadRegExScan [--pid <PID>] --pattern "<REGEX>"

# --- Volatility 2
volatility -f <MEMORY_DUMP_FILE> --profile=<PROFILE> yarascan [-y <YARA_RULES_FILE> | -Y "<STRING | YARA_RULE>"] [-p <PID>]
```

### Local persistence

The [`winesap`](https://github.com/reverseame/winesap) plugin (ported to
`Volatility 3` in 2026) and the `Volatility 2`
[`autoruns`](https://github.com/tomchop/volatility-autoruns) plugin can be
used to detect local persistence from a memory image. The plugins are
complementary as, while having some overlap, they enumerate different
persistence `ASEPs`.

The `ASEPs` covered by the `autoruns` plugin are the `HKLM\SOFTWARE` and
`NTUSER.DAT` registry `ASEP` keys, Windows services and scheduled tasks,
`Winlogon` `ASEP` entries, Active Setup
(`Microsoft\Active Setup\Installed Components`), and Microsoft Fix-it
(`Microsoft\Windows NT\CurrentVersion\AppCompatFlags\InstalledSDB`) entries.
More details can be found in the project's README. The registry-based
persistence `ASEPs` covered by `winesap` are detailed in the project's README
and
[taxonomy diagram](https://github.com/reverseame/winesap/blob/master/img/taxonomy.png).

```bash
# --- Volatility 3
# --match: only displays the suspicious entries.
vol -p <WINESAP_FOLDER> -f <MEMORY_DUMP_FILE> winesap.Winesap [--match]
vol -f <MEMORY_DUMP_FILE> windows.registry.scheduled_tasks.ScheduledTasks

# --- Volatility 2
volatility --plugins=<WINESAP_FOLDER> -f <MEMORY_DUMP_FILE> --profile=<PROFILE> winesap [--match]
# -v: displays the entries normally filtered (such as services from the System32 folder).
# -t: limits the search to the specified ASEP type(s), among autoruns (Run, RunOnce, etc.), services, appinit, winlogon, tasks, and activesetup.
volatility --plugins=<AUTORUNS_FOLDER> -f <MEMORY_DUMP_FILE> --profile=<PROFILE> autoruns [-v] [-t <ASEP_TYPE | COMMA_SEPARATED_ASEP_TYPES>]
```

## Linux memory analysis

### Symbol tables and profiles

Contrary to Windows memory images, for which the symbols are automatically
retrieved by `Volatility 3`, the analysis of Linux memory images requires a
symbol table (`Intermediate Symbol Format (ISF)` JSON file for
`Volatility 3`, profile for `Volatility 2`) matching exactly the kernel of the
analyzed system. For `Volatility 3`, the banner of the symbol table must match
exactly the banner of the kernel found in the memory image (including the
compilation information).

Pre-generated `Volatility 3` symbol tables for a large number of kernels of
the main Linux distributions are available in the
[`volatility3-symbols`](https://github.com/Abyss-W4tcher/volatility3-symbols)
community repository, and can be automatically retrieved using the
`--remote-isf-url` option.

Otherwise, the symbol table must be generated using
[`dwarf2json`](https://github.com/volatilityfoundation/dwarf2json), from the
kernel with debugging symbols (`vmlinux` file, which is notably provided by the
`linux-image-<KERNEL_VERSION>-dbgsym` package on Ubuntu and by the
`kernel-debuginfo` package on Red Hat-based distributions) matching the banner
of the memory image.

```bash
# Identifies the kernel banner(s) of the memory image (version and compilation information).
vol -f <MEMORY_DUMP_FILE> banners.Banners

# Uses the volatility3-symbols repository to automatically retrieve the matching symbol table.
vol --remote-isf-url 'https://github.com/Abyss-W4tcher/volatility3-symbols/raw/master/banners/banners.json' -f <MEMORY_DUMP_FILE> <PLUGIN>

# Generates the symbol table from the kernel with debugging symbols (and, optionally, the System.map file).
git clone https://github.com/volatilityfoundation/dwarf2json && cd dwarf2json && go build
./dwarf2json linux --elf <VMLINUX_WITH_DEBUG_SYMBOLS> [--system-map <SYSTEM_MAP_FILE>] > <KERNEL_NAME>.json

# The symbol table (that can be compressed with xz) must then be placed in the volatility3/symbols/linux/ folder, or in a folder specified with -s <SYMBOLS_DIR>.
vol -s <SYMBOLS_DIR> -f <MEMORY_DUMP_FILE> <PLUGIN>
```

For `Volatility 2`, which integrates a limited number of profiles for Linux
systems, the profile must be generated on the analyzed system or on a system
matching the analyzed system (identical Linux distribution, kernel version,
and CPU architecture). Refer to the
[`Volatility 2` documentation](https://github.com/volatilityfoundation/volatility/wiki/Linux#Linux-Profiles)
for more information on the required tools and build steps.

```bash
# Installs the prerequisite tools on Debian / Ubuntu systems.
apt-get install dwarfdump build-essential linux-headers-$(uname -r)

# Generates the Volatility 2 profile (as a ZIP file).
# The generated ZIP file must be transferred to the system with Volatility installed (in the <VOLATILITY_INSTALL>/volatility/plugins/overlays/linux/ folder or the plugin folder specified with --plugins=).
git clone https://github.com/volatilityfoundation/volatility.git
cd volatility/tools/linux && make
zip $(uname)_$(uname -r)_$(uname -m)_profile.zip module.dwarf /boot/System.map-$(uname -r)
```

### Volatility 3 usage

```bash
# Processes, with their command line and environment variables.
# --threads: includes the user threads.
# --dump: extracts the executable of the listed processes.
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> linux.pslist.PsList [--pid <PID>] [--threads] [--dump]
vol -f <MEMORY_DUMP_FILE> linux.pstree.PsTree [--pid <PID>]
vol -f <MEMORY_DUMP_FILE> linux.psscan.PsScan
vol -f <MEMORY_DUMP_FILE> linux.psaux.PsAux [--pid <PID>]
vol -f <MEMORY_DUMP_FILE> linux.envars.Envars [--pid <PID>]

# Bash history, recovered from the memory of the bash processes.
vol -f <MEMORY_DUMP_FILE> linux.bash.Bash [--pid <PID>]

# Network connections and interfaces.
vol -f <MEMORY_DUMP_FILE> linux.sockstat.Sockstat
vol -f <MEMORY_DUMP_FILE> linux.ip.Addr

# Open files, memory mappings, and memory-mapped ELF files of processes.
vol -f <MEMORY_DUMP_FILE> linux.lsof.Lsof [--pid <PID>]
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> linux.proc.Maps --pid <PID> [--dump]
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> linux.elfs.Elfs --pid <PID> [--dump]

# Files in the page cache: listing, extraction of the specified file, and recovery of the cached file system (as a compressed tarball).
vol -f <MEMORY_DUMP_FILE> linux.pagecache.Files [--find <FILE_PATH>]
vol -o <OUTPUT_DIR> -f <MEMORY_DUMP_FILE> linux.pagecache.InodePages --find <FILE_PATH> --dump
```
